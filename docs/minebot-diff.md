## 2. 值得抄的那两件，具体能实现什么

### A. 进度监督器（确定性，不需要快模型）
**现在的问题**：她卡住时没人管。我们的日志里最长静默 290 s（soak1 的 02:25–02:30，她在地下一路长挖），
我的审计只能事后说「这段时间没事件」，不能让她**当场**恢复。

**抄过来能得到**：
- 5 s 无进展 ⇒ 先做**有界诊断**（读一次世界状态，最多 2 次），而不是无限等；
- 诊断确认受阻 ⇒ **真停**（cancel + settle），把**已完成的部分**记下来；
- 把「卡在哪、已经拿到什么」作为**事实**交回给模型，让她换法；
- 全部有界（次数/时长都有上限），不会自己变成新的死循环。

**成本**：中等。需要「进展」的定义（我们的 `act` 时间戳 + 背包/位置变化即可），和一次 cancel 语义。

### C. 结构化世界真相（便宜且立刻有用）
**现在的问题**：`[act]` 里已经有 `ok/reason`，但进入提示词的是**聊天文本**。她于是会「以为自己做完了」。

**抄过来能得到**：每步之后她看到的是
`collected oak_log 3/4（还差 1）；上一步 mine 失败：no_path`
而不是「我刚砍了树」。
⇒ 直接减少「说做了其实没做」（我们的 `said-vs-did` 指标会降）。

**成本**：低。我这边已有的 `[act]` 契约 + 分类器，只要在拼提示词时把它渲染成 2–3 行事实即可。

## 3. 千万别抄的那件，和他们自己给的反证

MineBot 的 README 把 reflex 层写成卖点（「fast semantic model judges each step」），但**他们自己的实验文档**写得很清楚：

- 单帧误判 ≈ **1%**（159 帧里 3 次错），可这个问题**每秒问一次**、一次工作问 **30–60 帧** ⇒ 误停成为常态；
- 真实运行 **7 次停下里 3 次是误停**；
- 「被打断 1 次还是 5 次」对它的判断**完全没影响**（概率全在 0.18–0.21 平着）；
- 把「背包刚变了」写进上下文，会让它判「已完成」（0.65 → 0.74 判错）。

⇒ **用一个小模型去猜「做完了吗」，在工程上是不可靠的。** 我们已经有确定性信号（`ok`、数量、坐标），
应该用它，而不是再加一个会误判的裁判。**这也解释了为什么他们要把 reflex 标成 active/under development。**

---

## 4. 我们不需要抄的部分（避免白干）

- **身体层**：真客户端 + Baritone 的可靠性我们短期追不上，但那**不是产品瓶颈**（玩家要的是"她在动"，不是"她走得优雅"）。
- **治理层**：我们有 `protect.js` + 不滥用传送 + `op-fill` 单独记账，够用。
- **相机/观察者**（`camera/`）：我们不需要本地画面。
- **Python/Responses API 技术栈**：换栈的代价远大于收益（我们已把记忆/审计/人格都写在 Node 侧）。

---

## 5. 一句话
**MineBot 比我们多的，是「卡住之后怎么办」这一块工程纪律（监督器 + 结构化真相）；比我们少的是「她是谁、记得什么、说没说谎」。**
前者可以两天内补上（确定性实现，不引入快模型）；后者才是我们的东西。

## 修订（2026-10-25，依据 GPT 评审 #3004；我的原文有过推，逐条记下不删）

**① A 的 290 s 静默：不是已证明的停滞。** #2978 原文说她当时在用长 `!newAction` 挖，"not a statue" ⇒ 这首先暴露的是**观测缺口**（我们看不出她在干什么），**不能直接推出"加监督器就能恢复"**。另据 #2991/#3003，已有脱困提示与动作超时改动（桥内报告，我未核验实现）。
"5–10 秒发现并恢复"**承诺过头**：发现疑点、确认受阻、停止、恢复是**四件事**，只有第一件被他们测到了 7 s。

**② B 的统计口径错了（最需要修正的一条）**：
- `3/159 = 1.89%`（我原文写 ≈1% 是圆得过了）；
- `3/7` 是**"已发生的停止中误停占比"**，**不是每次任务的误停率**；
- 由"逐帧错误率"推"误停率"**还缺**错误类型、停止门槛、帧间相关性 —— 即便假设独立，`1-(1-p)^n` 算出的也只是"至少一次判断错"，未必导致停止；
- "打断次数不改变评分"**不能证明**该信息完全没进入判断。
⇒ **可成立的表述只有**：*这版模型 + 提示词 + 停止策略在该实验中出现了误停，因此不宜直接授予它停止权* —— 不能推广成"reflex 机制整体不可靠"（他们 README 也自标 under development）。

**③ C 的形式不等于内容。** 把 `ok/reason/msg` 显示成表格式，**不会自动产生"3/4"**；要知道**任务要求、起始数量、当前实测数量、采样时间**这四样，且 `act.ok` **未必**等于世界后置条件成立。原文"直接压 said-vs-did"应改为"**有望**减少"。

**④ D 不会自动让自由度指标有效。** 注册表总数仍可能恒定；**必须记录"本次实际提供给模型、且当前可执行的候选集"**，否则 `menu_size` 还是量不到选择空间。另：正文写 56 个命令、请求里 52 个，**口径要统一**。

**⑤ E 的理由收窄。** "抄了就失去安装性"是**绝对化推断** —— WSL2 是他们当前的开发支持环境，不必然等于玩家必须手装的全部依赖。可保留"不迁移"的决定，但理由改成：**当前工具链会增加部署成本**，就到这里。

**⑥ 我漏了更要紧的一类：动作生命周期与控制权**（不是保护区规则）。该问的是：
- 普通聊天能否**保留在途动作**？
- 显式停止是否**完成结算**？
- 恢复会话是否**保留目标而不重放已提交动作**？
- 旧调用结果**是否仍关联原调用**？

`protect.js` + OP 记账**覆盖不了**这些。但 #3003 已报告我们有 `runId` 隔离 ⇒ **不能写"完全缺失"**，应检查剩余缺口是否包含**旧动作继续改世界**与**控制权交接**。

**⑦ 删掉一句无依据的话**：原文末句"他们比我们少记忆、说没说谎"**站不住** —— RUNTIME 描述了持久任务、计划与真实世界验收。应改为**覆盖范围不同**，不能从未评估推成没有。

**⑧ 优先级改为先做 C，不做 A。** 理由：当前最明确的问题是**事实缺失、结果含糊**；290 s 那个案例**尚未证明**需要新增取消器，而且已有超时/提示机制的报告。
今天的 C 交付**限定为一件**：把一个常用动作的**真实后置事实**送进模型下一次输入，例如
`目标 +4；起始 0；实测 3；尚差 1；采样时间 …`；**读不到就写"未知"**。仅重排已有字符串**不算**完成，也先不做"全世界事实平台"。

**⑨ A 若真要做，最大的翻车点是"以为停了，身体还在执行"**：
- `[act]` 若只在 skill 返回时记录，长动作**正常执行期间也没有事件** ⇒ 每 3 s tick 读不到结束事件，**不能证明没有进展**；
- 坐标/背包变化必须**对应目标**：原地挖硬块可能有进展，绕圈或捡无关物品则没有；**固定 5 秒不适合当通用停止条件**；
- 若监督检查与等待长动作在**同一串行循环**里，它会跟着一起等；独立运行又要处理**重入与控制权竞争**；
- **Promise 超时 / abandon 不会取消 mineflayer 操作**：旧任务可能继续挖、继续走，甚至**随后清掉新任务的寻路目标**；`runId` 能挡旧结果污染状态，**不一定能挡旧代码继续操作世界**；
- `settle` 本身也**必须有截止时间**；停止未确认时**不能报"已停止"**并启动冲突动作。
⇒ **关键验收场景**：*旧动作收到取消后仍继续运行、随后才返回* —— 看它会不会再改世界、覆盖新任务状态、或停掉新任务。
